# 本轮进展（goal round 13/256）

## 结论：`channel_bar` 规则能布防，但在实机上**未被调用**

尝试了三种能触发频道列表重建的操作（冷启动 / 点另一个频道再点回首页 / 首页下拉刷新），
日志里始终**没有 `hit=channel_bar`**；能看到的 `channel_bar=…` 都只是安装表里的字段。

即：`com.tencent.channelnav.impl.r1.C()` 在这些流程里没被走到。可能原因（按可能性排序）：
1. **频道列表在首个 Activity 之前就已装配完成** —— 我的规则是在第一个 Activity 的
   `onCreate` 时安装的（因为 `onPackageReady` 时拿不到 Context，见 round 11 之前的排查），
   首次数据装配可能早于这个时点，因此错过；之后的重建又恰好没走 `C()`。
2. `impl.r1.C()` 只是**门面方法之一**，真正被 UI/redux 使用的是某个实现类的 `C()`
   （子代理已指出三套实现：`ChannelNavDataManager.A0` / `ChannelNavDataManagerOpt.K0` / `uitls.k.b`）。
3. 当前设备命中的是 V2 变体，而 V2 走的路径与 `r1.C()` 不同。

**下轮做法（明确，二选一）**
- **A：改挂三个实现的入口**，并同时保留 `r1.C()`（各自独立 id），这样无论哪个变体是活的都能拦到；
- **B：不依赖任何"装配出口"**，改 hook App **自带黑名单 getter**
  `com.tencent.channelnav.uitls.q.y()`，把我们想隐藏的频道 **id** 并进去
  —— 这是 App 官方过滤路径，且三个数据管理器**都**读它（子代理已验证），
  命中概率最高；代价是只能按 **id**（频道 id 服务端下发，dex 内无静态 id→名字映射，
  需要运行期先 dump 一次 id→名字）。
- 若走 B，需要先加一个"一次性 dump 频道 id/名字"的诊断（挂在首次命中行上），
  拿到映射后再固化到设置里。
